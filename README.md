# wiki-interest — навичка AI-агента для аналізу інтересу до тем у Wikipedia

Навичка у форматі [Agent Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills) допомагає засновникам B2C-продуктів
вирішувати, **які теми розвивати і якими мовами запускатися**. Для цього вона аналізує статистику переглядів
Wikipedia (Wikimedia Pageviews API) у різних мовних розділах. На виході — тренди з оцінкою надійності,
графік і PDF-звіт на одну сторінку.

```
wiki-interest/                     # корінь навички = корінь репозиторію
├── SKILL.md                       # інструкція для агента: що запускати і як читати результат
├── README.md
├── CLAUDE.md                      # контекст для Claude Code при розробці самої навички
├── pyproject.toml                 # лише налаштування pytest
├── requirements.txt               # requests, numpy, matplotlib
├── requirements-dev.txt           # + pytest, openai (для evals)
├── scripts/
│   ├── wi                         # лаунчер: створює .venv (у корені або XDG), запускає CLI
│   └── wiki_interest/
│       ├── cli.py                 # argparse і команди resolve / analyze / show / runs / report
│       ├── pipeline.py            # тема → статті → ряди → analysis.json; імена run
│       ├── interpret.py           # вердикти, попередження, каркас відповіді, таблиця, примітки (uk/en)
│       ├── stats.py               # сплески, сезонність, зростання, тренд, бал надійності
│       ├── wiki.py                # Wikipedia / Wikidata / Pageviews API
│       ├── http.py                # HTTP + дисковий кеш, повтори, офлайн-режим
│       ├── paths.py               # де лежать venv / runs / кеш; шляхи відносно папки агента
│       ├── charts.py              # PNG-графіки
│       └── report.py              # PDF на 1 сторінку
├── references/
│   └── METHODOLOGY.md             # формули, пороги, обмеження (агент читає за потреби)
├── tests/                         # pytest: по файлу на шар + end-to-end через CLI на фейковому API
└── evals/                         # сценарії із завдання, калібрування, транскрипти прогонів на Haiku
```
Залежності без циклів: `cli` → `pipeline` → `interpret` → `stats`; `pipeline` → `wiki` → `http`; `pipeline`, `report` → `charts`;
`http`, `pipeline`, `interpret` → `paths`.
Тексти, які бачить користувач, живуть лише в `interpret.py`; математика — лише в `stats.py`.
Згенеровані `.venv/`, `.cache/` і `runs/` лежать у корені й ігноруються git. Якщо корінь лише для читання, вони
переїжджають у `${XDG_DATA_HOME:-~/.local/share}/wiki-interest` і `${XDG_CACHE_HOME:-~/.cache}/wiki-interest`
(перевизначення: `WIKI_INTEREST_HOME`, `WIKI_INTEREST_RUNS`, `WIKI_INTEREST_CACHE`).

## Швидкий старт

```bash
cd wiki-interest
scripts/wi analyze --topic "Intermittent fasting" --langs pl,cs      # перший запуск сам поставить залежності
scripts/wi report runs/<run> --title "Інтервальне голодування: pl vs cs" --conclusion "…"
```

Потрібен лише Python ≥ 3.9 (перевірено на системному Python 3.9 у macOS). `.venv` створює перший запуск
`scripts/wi`; якщо встановлення перервалося, наступний запуск його довершить. Щоб підключити навичку до агента
(Claude Code та інших), скопіюйте директорію в `~/.claude/skills/` або `.claude/skills/` проєкту.
Wikimedia просить указувати контакт у User-Agent: без нього ліміт — 10 запитів на хвилину замість 200.
Типовий User-Agent містить URL цього репозиторію; для власного розгортання задайте свій:
`export WIKI_INTEREST_UA="my-app/1.0 (https://my-site.example; me@my-site.example)"`.

## Логіка роботи

1. **Тема → поняття, а не ключове слово.** Пошук у Wikipedia дає кандидатів. Сторінки неоднозначностей
   пропускаються, решта кандидатів повертається як `alternatives`, щоб агент міг перевірити вибір. Далі
   Wikidata sitelinks дають назву **тієї самої статті** в кожній мові. Так «Intermittent fasting» у pl і cs
   гарантовано означає одне й те саме поняття, а не два різні переклади. Для абстрактних запитів
   («вивчення англійської») агент обирає proxy-статтю, може сумувати кілька статей (`A+B`) і має назвати
   користувачеві, що саме він міряв.
2. **Дані.** Беруться лише місячні перегляди з `agent=user`, тобто без ботів. Поточний неповний місяць
   виключається. Для кожної мови завантажується ще й сумарний трафік усього мовного розділу.
3. **Статистика, якій можна довіряти** (детально в [METHODOLOGY.md](references/METHODOLOGY.md)):
   - сплески (новини, віральні пости, боти) шукаються через robust z-score відносно ковзної медіани.
     Їх видно на графіку, але з головної метрики вони виключені. Пік, що повторюється в тому самому
     місяці щороку (вересень для астрономії), вважається сезонністю: він не вирізається, бо порівняння
     рік до року його вже нейтралізує. Лишається лише сезонна частина піку: викид поверх нього відрізається;
   - нова або перейменована стаття: місяці до появи назви не рахуються даними (див. сьому ітерацію);
   - головна метрика — останні 12 місяців проти попередніх 12. Порівнюються ті самі календарні місяці,
     тому сезонність (січневі дієти, вересень для навчання) скорочується;
   - **відносна зміна** — частка статті в усьому мовному розділі. Вона прибирає ефект на зразок
     «вся Wikipedia втрачає трафік через AI-відповіді в пошуку». Напрям рахується і для переглядів, і для частки;
     якщо вони розходяться, вердикт називає обидва;
   - тренд Тейла–Сена, тест Манна–Кендалла і кількість місяців із 12, що перевищили той самий місяць
     минулого року;
   - **надійність 0–10 → high/medium/low** із шести складників (обсяг, значущість, узгодженість місяців зі знаком
     зміни, вплив сплесків, узгодженість із нормалізацією, ≥ 24 міс. даних) з поясненнями людською мовою. Малий обсяг переглядів обмежує
     оцінку згори: 55 переглядів на місяць не можуть дати «високу» надійність. Таке обмеження явно видно
     в таблиці (`low (8/10, volume cap)`), тож модель не сприйме його як суперечність.
4. **Відповідь і звіт.** Агент не рахує і не формулює висновки про тренд сам: він цитує готові речення
   `verdicts`. Висновок у PDF пише агент, а цифри, графік, таблиця і розділ «Припущення та обмеження» (зокрема
   примітки про proxy і низьку надійність) генеруються кодом.

### Рішення, орієнтовані на слабку модель (Haiku-клас)

- **Одна команда на типовий запит.** `analyze` сама робить пошук, завантаження, статистику і графік.
  Моделі не треба планувати ланцюжок кроків.
- **Компактний вивід.** Markdown-таблиця вже відсортована, у `details` лежать причини, а сирі ряди не
  друкуються, щоб не забивати контекст. Помилки повертаються як `{"error", "hint"}`, а не як traceback.
- **Попередження з готовими командами.** Якщо мовного розділу немає у Wikidata або proxy-стаття має
  мізерний трафік, `analyze` повертає `warnings` з точною наступною командою (`resolve --search-lang`,
  `--article lang:Title`, ширша стаття). Підказка `next` використовує `scripts/wi`, а не системний `python`,
  у якому немає залежностей.
- **Готова інтерпретація.** Для кожної мови код видає речення-вердикт (напрям, цифри, надійність, сезонність,
  proxy). Модель його цитує, тож не може назвати шум «зростанням» або змішати цифри з різних колонок. Чи є
  стаття proxy (іншим поняттям), визначає код через Wikidata, а не модель.
- **Повторні й пов'язані запити дешеві.** Перегляди кожної статті запитуються двома канонічними діапазонами
  (закрита історія з 2015 року — кешується назавжди, останні 3 місяці — на 24 години), тому будь-який період
  («візьми 3 роки», «з 2019-го») береться з кешу без жодного запиту, а «додай словацьку» докачує лише
  словацьку. Кожне окреме питання (теми × мови × період)
  зберігається в окрему директорію, тож уточнення не перезаписує попередній результат. `runs` і `show` дають
  повернутися до попереднього аналізу без мережі.
- **Відтворюваність.** Лише 3 залежності, venv створюється автоматично, скомпільованих файлів немає.

## Як перевірялася якість

| рівень | що перевіряє | як запустити |
|---|---|---|
| Unit | Манна–Кендалл на відомих рядах; виявлення сплеску, після прибирання якого «зростання» зникає; розбіжність нормалізації; межі місяців (лютий високосного року) | `.venv/bin/pip install -r requirements-dev.txt && .venv/bin/python -m pytest` |
| End-to-end без мережі | фейковий API з відомими властивостями (pl росте, cs — пласка зі сплеском, uk — мізерний обсяг, en падає): пошук пропускає «(film)», знаходить відсутню мову, правильно визначає напрям і надійність, генерує PNG і PDF | те саме |
| Повний сценарій на дешевій моделі | 4 кейси із завдання, зокрема багатокроковий уточнювальний. Перевіряє, які команди запустила модель, що є у відповіді і чи створено PDF (у власній порожній `runs/` кожного кейсу); `--repeat N` дає частоту проходження кожної перевірки; транскрипти — в `evals/transcripts/` | `OPENROUTER_API_KEY=… .venv/bin/python evals/run_agent.py --model anthropic/claude-haiku-4.5 --repeat 5` |
| Калібрування статистики | тисячі синтетичних рядів з відомою правдою і реальним рівнем шуму: як часто пласка тема отримує «зростає», яку частку справжнього росту знаходимо; Theil–Sen і Mann–Kendall звірено зі `scipy` | `.venv/bin/python evals/calibrate_stats.py` |
| Звірка даних | місячні перегляди, які бере інструмент, проти суми денних даних API (їх показує pageviews.wmcloud.org): 6 статей × 36 міс., усі 216 значень збіглися | результати в [METHODOLOGY.md](references/METHODOLOGY.md#data-cross-check) |

Рев'ю на реальних даних знайшло ще кілька проблем, і на кожну тепер є регресійний тест: підказка з
`python -m` падала без venv; уточнення «додай мову» перезаписувало попередній run разом зі звітом;
для першого прикладу із завдання польської статті немає у Wikidata, а спосіб додати локальну статтю не був
описаний; рекомендована proxy-стаття для «вивчення англійської» мала 10–150 переглядів на місяць (заміна на
«English language» дає 7–29 тис. і високу надійність); вересневі піки астрономії позначалися як аномалії.
Перевірка з порожнім кешем знайшла ще одну: без контакту в User-Agent Wikimedia дає лише 10 запитів на
хвилину, і запит на 15 мов падав з HTTP 429 (кеш під час розробки це приховував). Тепер User-Agent містить
URL проєкту, а клієнт у разі 429 чекає стільки, скільки каже `Retry-After`, і продовжує з місця зупинки.

Тести вже впіймали реальну помилку: шумний ряд із медіаною 55 переглядів на місяць отримував «medium»,
бо легко набирав бали за відсутність сплесків. Після цього з'явилися жорсткі обмеження за обсягом.

Фінальний аудит перед здачею (прогін `--langs top:15` і PDF з крайніми випадками) знайшов ще чотири проблеми,
на кожну є регресійний тест: PDF мовчки показував лише перші 10 серій у порядку введення, тож для «English
language» у 15 мовах випадали `fa` і `tr` — єдині з ростом частки (тепер серії відсортовано як у таблиці, а вивід
`report` каже, скільки показано); назви статей CJK-мовами друкувалися квадратами, а попередження matplotlib
засмічували stderr агента (тепер шрифти системи підключаються як fallback, а нечитабельна назва замінюється
англійською назвою поняття з приміткою); задовгий висновок обрізався без попередження (тепер спочатку меншає
шрифт, а обрізання повертається як `conclusion_truncated` з підказкою); помилки argparse йшли в stderr текстом,
а не JSON. Заодно обіцянка «зміна періоду не докачує нічого» стала правдою: раніше ключ кешу містив діапазон дат.

### Прогін на Claude Haiku 4.5 (2026-09-23)

Чотири кейси з `evals/cases.json` прогнано на **Claude Haiku 4.5** як агенті Claude Code. Агент отримував лише
шлях до навички та запит користувача, без підказок. Це не `evals/run_agent.py` через OpenRouter, тому автоматичні
перевірки не запускалися: результат оцінено вручну. Кожну цифру у відповідях звірено з `analysis.json`
відповідного run.

| кейс | команди | виклики інструментів / токени / час | результат |
|---|---|---|---|
| Астрономія, uk, «чи можна довіряти» | `analyze` | 3 / ~34k / 47 с | ✅ цифри точні; вересневі піки названо сезонністю; надійність з причиною. Не згадано «перегляди ≠ готовність платити» |
| Інтервальне голодування, pl vs cs | `analyze` → `resolve --search-lang pl` → `analyze --article pl:Post` | 7 / ~39k / 79 с | ⚠️ пішов за `warnings` і чесно назвав proxy, але не попередив, що порівнює різні поняття |
| Вивчення англійської, 5 мов + PDF | `analyze --topic "English language"` → `report` | 4 / ~37k / 79 с | ⚠️ сам обрав широку статтю, у всіх мовах висока надійність, PDF створено. Але додав факти, яких немає в даних («активна tech-спільнота», португальські ринки без даних) |
| Уточнення: + словацька, 3 роки | 2 ходи, 7 команд, `--months 36`, `--article sk:Pôst` | 10 / ~46k / 137 с (обидва ходи) | ⚠️ контекст збережено, новий run не перезаписав попередній. Одна помилка в цифрах: тренд sk −29 %/рік названо «−47–52 % на рік». У першому ході сказав «інтерес ЗРОСТАЄ» при `direction = flat` |

**Що це показало.** Код і формат виводу працюють: жодної помилки виконання, модель завжди вкладалася в 1–7 команд,
а виправлення з рев'ю (попередження з командами, окремі run, ширша proxy-стаття) модель використала без підказок.
Слабке місце — інтерпретація: модель ігнорує правила, записані лише прозою в SKILL.md.
Найцікавіше спостереження: польська «Post» і словацька «Pôst» мають сезонні піки в березні. Це Великий піст, тобто
proxy міряє релігійний піст, а не інтервальне голодування. Модель цього не помітила.

#### Друга ітерація: правила з прози — у код

Що змінено за результатами першого прогону:
1. **Proxy визначає код.** Для статті, доданої через `--article`, код бере її Wikidata-елемент. Якщо це інше поняття,
   ніж тема, то в таблиці з'являється `Post [proxy]`, у `warnings` — пояснення, а в PDF — обов'язкова примітка,
   незалежно від того, що напише модель.
2. **`verdicts`:** для кожної мови готове речення з напрямом, цифрами, надійністю, сезонністю і позначкою proxy.
   Модель його цитує, а не формулює. Якщо перегляди змінились, а частка в розділі — ні, вердикт прямо каже, що
   це зміна трафіку всього розділу.
3. **«Жорсткі правила»** винесено на початок SKILL.md; в evals додано негативні перевірки (`answer_not`) для
   вигаданих фактів із першого прогону.

Повторний прогін тих самих кейсів з тими самими промптами на Haiku 4.5:

| кейс | прогін 1 | прогін 2 |
|---|---|---|
| Астрономія, uk | ✅ без рядка «≠ готовність платити» | ✅ рядок є; ⚠️ не згадав сезонні піки з вердикту |
| Голодування, pl vs cs | ⚠️ proxy «Post» без попередження про інше поняття | ✅ цитує вердикт; «пряме порівняння неможливе»; рядок про оплату є |
| Англійська, 5 мов + PDF | ⚠️ вигадані факти про ринки | ✅ вигаданих фактів немає; PDF-висновок спирається на частку в трафіку розділу; ⚠️ у чаті не ранжував 5 аудиторій, без рядка про оплату (у PDF є автоматично) |
| Уточнення: + sk, 3 роки | ⚠️ «ЗРОСТАЄ» при `flat`; змішані цифри | ✅ цифри точні; кандидатів у pl перевірив через `resolve` і відкинув; ⚠️ узагальнення поза даними («тема маргіналізована в регіоні»), без рядка про оплату |

Висновок: помилки, які контролює код (напрям тренду, цифри, proxy, примітки в PDF), зникли. Лишилися помилки
в тому, що модель пише від себе: пропущений рядок про обмеження (2 з 4 відповідей у чаті) і м'які узагальнення.
Наступний крок у тому самому дусі: віддавати не лише `verdicts`, а готовий каркас відповіді з обов'язковим
рядком обмежень, і перевіряти це тими самими evals.

#### Третя ітерація: готовий каркас відповіді

`analyze` тепер повертає `answer_skeleton`: повну відповідь (дані, вердикт по кожній мові, мови без статті,
порівняння мов за часткою в трафіку і за обсягом, рядок обмежень, графік) з одним місцем `<ЗАПОВНИ: …>` для
висновку. В evals додано перевірки, що місце заповнене і що у відповіді про астрономію згадано сезонність.

| кейс | прогін 2 | прогін 3 |
|---|---|---|
| Астрономія, uk | ✅; ⚠️ без сезонних піків | ✅ каркас скопійовано повністю: сезонність, обмеження, заповнене місце; цифри звірено |
| Голодування, pl vs cs | ✅ | ✅ сам порівняв однакове поняття «Fasting» в обох мовах (коректне порівняння); ⚠️ відповідь своїми словами, без рядка обмежень |
| Англійська, 5 мов + PDF | ⚠️ не ранжував аудиторії | ✅ ранжує аудиторії за рядком порівняння (vi, tr — першими); ⚠️ без каркаса і рядка обмежень; «vi — єдина, що росте», хоча tr теж +0.6 % |
| Уточнення: + sk, 3 роки | ⚠️ узагальнення, без обмежень | хід 1: ⚠️ без каркаса; хід 2: ✅ каркас з обмеженнями; ⚠️ у висновку знову узагальнення на регіон |

Висновок: де модель бере каркас, відповідь повна і правильна. Але Haiku копіює його лише у 2 з 5 відповідей,
переважно після однієї команди `analyze`. Після кількох кроків (пошук статті, повторний аналіз) модель пише
відповідь сама. Межа формату навички: текст відповіді в чаті навичка лише пропонує, а гарантує тільки те, що
генерує код (цифри, вердикти, PDF із примітками). Тому обов'язкові речі дублюються в PDF, а evals ловлять решту.

#### Четверта ітерація: гіпотеза не підтвердилась (відкочено)

Гіпотеза: модель копіює каркас рідко, бо він стоїть посередині JSON одним рядком із `\n`. Спроба: перенести
`answer_skeleton` в кінець виводу (останнє прочитане) і віддавати його масивом рядків.

| | прогін 3 (каркас посередині) | прогін 4 (каркас в кінці, рядками) |
|---|---|---|
| каркас скопійовано повністю | 2 з 5 відповідей | 0 з 5 (1 частково) |
| рядок обмежень у чаті | 2 з 5 | 0 з 5 |
| помилки в цифрах | 0 | 0 |

Покращення немає, тому зміну відкочено до варіанта прогону 3. Головний висновок цієї ітерації: при одному запуску
на кейс розкид між запусками більший за ефект таких правок. Та сама модель на тому самому кейсі (астрономія)
скопіювала каркас у прогоні 3 і не скопіювала в прогоні 4. Тому подальше налаштування тексту відповіді в чаті має
сенс лише з кількома запусками на кейс (`evals/run_agent.py` у циклі, наприклад 5 × 4 кейси) і порівнянням частот, а
не окремих відповідей. Стабільним у всіх чотирьох прогонах лишилося те, що генерує код: жодної помилки в цифрах
після другої ітерації, коректні `verdicts`, proxy і примітки в PDF.

| помилки виконання | 0 |

Висновки ті самі, що в ітераціях 3–4, тепер на більшій вибірці: усе, що генерує код, стабільне (команди, цифри,
proxy, PDF), а вільний текст у чаті — межа формату. Одну помилку вдалося перенести в код: у рядку порівняння мов
`vi +2.4% > tr +0.6%` модель бачила «ріст», хоча вердикти обох кажуть, що частка майже не змінилась. Тепер зміни в
межах ±10 % там позначено `(≈ без змін)`, тобто рядок порівняння більше не суперечить вердиктам (регресійний тест є).

Перевірки поза моделлю (деталі в [METHODOLOGY.md](references/METHODOLOGY.md#calibration-evalscalibrate_statspy)):
- **Калібрування.** Реальний шум статей виміряно (медіана 0.17 для місячної зміни в лог-шкалі). З таким шумом і
  початковим правилом (`p < 0.2`) пласка тема отримувала «зростає, висока надійність» у 8–14 % випадків: 24 місяці —
  коротка вибірка, а автокореляція робить p-value оптимістичним. Поправка Hamed–Rao на автокореляцію не допомогла.
  Для інвестиційного рішення хибне «зростає» дорожче за пропущений помірний ріст, тому поріг посилено до
  `p < 0.05`: хибні сигнали — 6–9 %, ріст +20 %/рік знаходимо в 59–68 % (було 72–79 %), +50 % — у 99 %.
  Пропущений ріст ділиться між «стабільний» і «дані не підтверджують тренд» (виправлено в сьомій ітерації: раніше тут
  було написано, що він потрапляє переважно в друге). Один вердикт «зростає» — це гіпотеза, як і написано в примітках.
- **Звірка даних** з незалежним розрахунком: 216 з 216 значень збіглися.
- **Порожній кеш і ліміти API**: див. вище (HTTP 429 без контакту в User-Agent).

| `evals/run_agent.py`: `runs/` спільна для кейсів, тож старий PDF зараховував кейс звіту; один прогін — шум; вивід інструмента обрізався на 8000 символів, а не як у Claude Code | кожен кейс має власну тимчасову `runs/` (`WIKI_INTEREST_RUNS`), `files` перевіряються в ній; `--repeat N` з частотою проходження кожної перевірки; межа 30 000 символів у константі | `test_each_case_gets_its_own_runs_dir`, `test_pass_rates_over_repeats`, `test_tool_output_is_cut_like_claude_code` |

Платний прогін моделі (`evals/run_agent.py`) у цій ітерації не запускався: зміни перевірено тестами й калібруванням.
Наступний крок — `run_agent.py --repeat 5` на Haiku 4.5, щоб побачити, чи модель цитує нові вердикти й додає
`--proxy-for` (перевірка вже є в `evals/cases.json`).

#### Восьма ітерація: перевірка виправлень сьомої

Повторне рев'ю тих самих виправлень знайшло ще п'ять проблем. Порядок той самий: спершу регресійний тест, який
падає, потім виправлення, кожне окремим комітом.

| проблема | як знайдено | виправлення | регресійний тест |
|---|---|---|---|
| `report runs/<name>` шукав шлях спершу від папки агента й від кореня навички і лише потім у налаштованій папці `runs`: при `WIKI_INTEREST_RUNS` (кожен кейс `evals/run_agent.py` має свою) застарілий `runs/<name>` у корені перемагав і отримував PDF — ізоляція кейсів не працювала | відтворення з `WIKI_INTEREST_RUNS=<tmp>` і копією run у корені | шлях, що починається з `runs/`, спершу шукається в налаштованій папці runs; інші відносні шляхи — як раніше (від папки агента, від кореня, за ім'ям) | `test_runs_prefix_is_looked_up_in_the_configured_runs_dir_first` |
| `test_launcher_works_from_a_read_only_skill_dir` падав під root: `chmod` не обмежує root, `[ -w ]` і `os.access` кажуть «записувано», тож копія навички не була read-only. На справжніх read-only монтуваннях (EROFS) код працює, симуляція — ні | запуск тестів у контейнері від root | `skipif(os.geteuid() == 0)` з поясненням у коментарі | той самий тест (пропускається під root, тут запускався від звичайного користувача) |

## Використання AI-інструментів

Код, тести й документацію писано з AI-асистентом. Результати перевірялися так:
- формули звірено з визначеннями (Theil–Sen, Mann–Kendall з поправкою на однакові значення, robust z через MAD);
- на кожну статистичну властивість є тест з очікуваним результатом, відомим заздалегідь;
- PDF переглянуто візуально: кирилиця, обрізані заголовки таблиці (виправлено), читабельність графіків;
- транскрипти evals анонімізуються (шляхи з іменем користувача ОС замінюються на `<skill>` і `~`), тому
  їх можна публікувати;
- поведінку моделі перевірено через `evals/` — на транскриптах видно, де модель помилялася, і за ними
  правилися SKILL.md та формат виводу.

## Як розвивати навичку далі

Кроки впорядковано за співвідношенням користі й зусиль:

1. **Набір eval-кейсів як основа ітерацій.** Кожен реальний запит, на якому агент помилився, стає кейсом
   у `evals/cases.json`. Будь-яку зміну SKILL.md чи виводу перевіряти на всіх моделях-цілях і стежити за
   pass rate, кількістю кроків і токенами. Для регресій потрібні заморожені фікстури реальних даних.
2. **Кращі теми.** Автоматичне розширення теми через Wikidata (P279/P361, «частина від») і пов'язані
   статті, пропозиція кластерів для абстрактних запитів, редиректи за замовчуванням для малих розділів.
3. **Глибша статистика.** STL-декомпозиція і seasonal Kendall для 3+ років, пошук точок зміни тренду
   (коли почалося зростання), bootstrap-інтервали для % зміни, денна гранулярність для аналізу сплесків,
   прогноз з інтервалами.
4. **Критерії перспективності користувача.** Конфіг ваг (ріст, розмір, частка, стабільність), з якого
   обчислюється opportunity score. Сюди ж зовнішні дані: кількість носіїв, інтернет-користувачі, ARPU
   ринку, Google Trends для перехресної перевірки. Також пам'ять припущень проєкту (`project.yaml`), щоб
   уточнення «рахуй лише мобільний трафік» зберігалися між запитами.
5. **Більші обсяги даних.** Сотні статей × десятки мов: асинхронне паралельне завантаження з
   rate-limit, кеш у SQLite/Parquet + DuckDB замість JSON-файлів, а для тисяч статей — місячні дампи
   pageviews замість API. У виводі агенту лише агрегати й топ-N, повні дані зберігаються у файлі.
6. **Складніші дослідження.** Багатосторінкові звіти, порівняння «тема × мова» у вигляді heatmap, пакетний
   режим (`batch.yaml` з десятками гіпотез), а також MCP-сервер поверх того самого ядра для агентів без
   shell-доступу.
